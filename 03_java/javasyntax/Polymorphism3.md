# ***다형성과 설계***

## 좋은 객체 지향 프로그래밍?

### *객체 지향 특징*
- 추상화
- 캡슐화
- 상속
- *다형성*

### *객체 지향 프로그래밍*
- 객체 지향 프로그래밍은 컴퓨터 프로그램을 명령어 목록으로 보는 것에서 벗어나 여러 개의 독립된 단위,
'객체'의 모임으로 파악하고자 하는 것이다. 각각의 *객체*는 메시지를 주고받고 데이터를 처리할 수 있다. (*협력*)
- 객체 지향 프로그래밍은 프로그램을 *유연*하고 *변경*이 용이하게 만들기 때문에 대규모 소프트웨어 개발에 많이 사용된다.
  
### 유연함과 변경이 용이하다는 건?
- 레고 블럭을 갈아 끼우듯이 바꿀 수 있고
- 컴퓨터 하드웨어를 갈아 끼우듯이
- 컴포넌트를 쉽고 유연하게 변경하면서 개발할 수 있는 방법

## *다형성*
완전한 동치는 아니지만 실세계에 비유하자면 다형성은 세상을 *역할*과 *구현*으로 구분한다.
  
연극에서 역할과 배우는 다르다. 극 중 역할을 배우가 맡는 것이니 배우가 바뀌어도 극에는 아무런 영향을 미치지 않는다.  
이 예시에서 역할은 말그대로 역할이고, 배우가 구현이 되는 것이다.  
글로벌한 역할은 존재하고 그 역할을 누가 맡느냐 ( 어떻게 구현하느냐 ) 는 역할에 영향을 미치지 못한다.

### 역할과 구현의 분리
- *클라이언트*는 대상의 역할 ( 인터페이스 ) 만 알면 된다.
- *클라이언트*는 구현 대상의 내부 구조를 몰라도 된다.
- *클라이언트*는 구현 대상의 내부 구조가 변경되어도 영향을 받지 않는다.
- *클라이언트*는 구현 대상 자체를 변경해도 영향을 받지 않는다.
  
자바에서는:
- 역할 = 인터페이스
- 구현 = 인터페이스를 구현한 클래스, 구현 객체
- 객체를 설계할 때 *역할*과 *구현*을 명확히 분리한다.
- 객체 설계시 역할을 먼저 부여하고 그 역할을 수행하는 구현 객체를 만든다.

## *객체의 협력이라는 관계*
- 혼자 존재하는 객체는 없다.
- 클라이언트: 요청, 서버: 응답
- 수 많은 객체 클라이언트와 객체 서버는 서로 협력 관계를 갖는다.

### 자바에서는?
- 오버라이딩을 생각하면 *메인* 메서드에서 *인터페이스* 에 요청을 보내고 (클라이언트) 그 인터페이스를 통해 서버 ( 구현체 )
의 응답을 받는다.


- 인터페이스를 구현한 객체 인스턴스를 실행 시점에 유연하게 변경할 수 있다.
- 다형성의 본질을 이해하려면 협력이라는 객체사이의 관계에서 시작해야함
- *클라이언트를 변경하지 않고, 서버의 구현 기능을 유연하게 변경할 수 있다.*

## 역할과 구현응 분리했을 때
### 정리
- 유연하고 변경이 용이하다.
- 확장이 편리하다.
- 클라이언트에 영향을 주지 않고 변경할 수 있다.

### 한계
- 인터페이스가 변하면 클라이언트와 서버 모두에 큰 변경이 발생한다.

# 총정리
- *다형성*은 매우 중요하다.
- 추후 배울 디자인 패턴 대부분은 다형성을 활용한다.
- 스프링의 핵심인 제어의 역전 (IoC), 의존관계 주입(DI)도 결국 다형성을 활용한다.
- 스프링을 사용하면 위에서 설명한 역할과 구현의 구분을 편하게 할 수 있다.

# 마치며
## OCP (Open - Closed - Principle) 원칙
- Open for extension: 새로운 기능의 추가나 변경 사항이 생겼을 때, 기존 코드는 확장할 수 있어야한다.
- Closed for modification: 기존의 코드는 수정되면 안된다.

확장에는 열려있고 변경에는 닫혀 있어야한다. 즉 기존의 코드 수정 없이 새로운 기능을 추가할 수 있어야한다는 의미이다.
